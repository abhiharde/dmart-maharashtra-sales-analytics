DMart ETL Project: From Snowflake Ingestion to Power BI
============================================================

VIDEO PURPOSE
-------------
This video explains a complete retail data engineering project using Snowflake,
dbt, and Power BI. The language is intentionally simple for beginners.

Suggested video title:
"Complete DMart ETL Project Using Snowflake, dbt, and Power BI"

Suggested length:
15 to 25 minutes


OPENING
-------
[Show the final Power BI dashboard]

Hello everyone. In this video, I will explain my DMart ETL project from start
to finish.

The project takes retail data, loads it into Snowflake, transforms it with dbt,
creates a clean analytical data model, and finally connects the Gold layer to
Power BI for reporting.

The business questions are simple:

- How much revenue did we generate?
- Which stores perform best?
- Which products and categories sell the most?
- Which payment methods do customers use?
- How does revenue change by date and season?

The final result is one interactive Power BI dashboard.


PROJECT ARCHITECTURE
--------------------
[Show the project folders and draw this flow on screen]

CSV files
   |
   v
Snowflake RAW_DATA schema
   |
   v
Bronze: raw pass-through models
   |
   v
Silver: cleaned and typed models
   |
   v
Gold: OBT, fact, dimensions, and KPIs
   |
   v
Power BI star-schema dashboard

The layers have different responsibilities:

Bronze keeps the original data close to its source.
Silver cleans and standardizes the data.
Gold prepares business-ready tables for analytics.
Power BI turns those tables into visual reports.

This layered design makes the project easier to understand, test, maintain,
and troubleshoot.


TOOLS USED
----------
[Show each tool briefly]

1. Snowflake stores the data and runs SQL transformations.
2. dbt Core manages SQL models, dependencies, tests, snapshots, seeds, and
   reusable macros.
3. Power BI connects to the Gold schema and creates the dashboard.
4. CSV files are the original sample data source.

The project uses the Snowflake profile named dmart_ETL_project.


SOURCE DATA AND SNOWFLAKE INGESTION
-----------------------------------
[Show the Raw files folder]

The project starts with four CSV files:

- calendar.csv: dates, months, years, weekdays, quarters, holidays, festivals,
  and seasons.
- products.csv: product, category, brand, price, supplier, and shelf-life data.
- sales_transactions.csv: invoices, stores, products, dates, quantities,
  prices, discounts, payments, and sales amounts.
- store_info.csv: store names, locations, types, opening dates, area, and
  manager information.

These files are loaded into Snowflake RAW_DATA tables. The dbt source file is
models/sources.yml. It tells dbt where the raw tables are located.

The source tables are:

- RAW_DATA.sales_transactions
- RAW_DATA.store_info
- RAW_DATA.products
- RAW_DATA.calendar

A source is not a transformation. It is a named reference to data that already
exists in the warehouse.

Important: the CSV loading step can be done with Snowflake stages, COPY INTO,
Snowpipe, or another ingestion process. dbt begins after the raw tables exist.


DBT PROJECT CONFIGURATION
-------------------------
[Open dbt_project.yml]

The main configuration file is dbt_project.yml.

It tells dbt:

- The project name is dmart_etl_project.
- Models are inside the models folder.
- Seeds are inside the seeds folder.
- Macros are inside the macros folder.
- Snapshots are inside the snapshots folder.
- Tests are inside the tests folder.

It also controls where models are created:

- Bronze models become views in DMART_ETL.BRONZE.
- Silver models become views in DMART_ETL.SILVER.
- Gold models become tables in DMART_ETL.GOLD.

Views are useful for lightweight transformation layers. Tables are useful for
Gold data that Power BI will query repeatedly.

The custom generate_schema_name macro makes the schema names exact. Without
this configuration, dbt can append custom schema names to the target schema.


BRONZE LAYER
------------
[Open models/bronze]

The Bronze layer has four models:

- bronze_calendar.sql
- bronze_products.sql
- bronze_sales.sql
- bronze_stores.sql

Each Bronze model is intentionally simple. It selects all columns from a dbt
source, for example:

    SELECT * FROM {{ source('raw_data', 'calendar') }}

Bronze is a landing or raw-preservation layer. It keeps the source structure
available inside Snowflake and gives later models a stable dbt reference.

The Bronze models are views in DMART_ETL.BRONZE.

Why use Bronze?

- We preserve the raw structure.
- We can inspect the data after ingestion.
- We separate ingestion from business transformations.
- We have a clear starting point for the Silver layer.


SILVER LAYER
------------
[Open models/silver]

The Silver layer contains four cleaned models:

1. silver_calender.sql
   Cleans the calendar data, casts the date, month, and year, standardizes
   weekday and season text, and converts the holiday flag to Boolean.

2. silver_products.sql
   Cleans product IDs and text fields, converts MRP and shelf life to numbers,
   and standardizes category, brand, supplier, and import-source values.

3. silver_sales.sql
   Cleans IDs and payment fields, converts the sale date and numerical sales
   fields, and converts return_flag into the Boolean column is_return.

4. silver_stores.sql
   Cleans store and location fields, converts opening_date to a date, converts
   area to a number, and converts latitude and longitude to decimals.

Each Silver model follows the same beginner-friendly pattern:

    source CTE -> cleaned CTE -> final SELECT

The ref function creates a dependency, for example:

    from {{ ref('bronze_sales') }}

This tells dbt that Silver depends on Bronze. dbt can then build models in the
correct order and create lineage information.

Examples of Silver transformations are:

- TRIM removes extra spaces.
- NULLIF converts blank text to NULL.
- TRY_TO_DATE safely converts text to a date.
- TRY_TO_NUMBER safely converts text to a number.
- INITCAP standardizes text casing.
- UPPER and LOWER standardize codes and units.
- COALESCE supplies a default when a value is missing.

The Silver models are views in DMART_ETL.SILVER.


GOLD LAYER AND ONE BIG TABLE
----------------------------
[Open models/gold/obt_sales.sql]

The first important Gold model is obt_sales.sql.

OBT means One Big Table. It joins the cleaned Silver sales, product, store,
and calendar models into one wide table.

The joins are:

- Sales product_id to product product_id.
- Sales store_id to store store_id.
- Sales sale_date to calendar calendar_date.

The model uses LEFT JOIN. This keeps a sales transaction even when a matching
product, store, or calendar record is missing. That is useful for investigation
and data-quality work.

The OBT contains transaction information together with descriptive attributes:

- Store name, city, state, type, and area.
- Product category, subcategory, brand, and MRP.
- Calendar year, month, weekday, quarter, holiday, and season.
- Quantity, price, discount, revenue, GST, payment, and return information.

The OBT is useful as a staging ground, but it is not the main Power BI table.
The final report uses the star schema tables.


GOLD FACT TABLE
---------------
[Open models/gold/fact_sales.sql]

fact_sales is the central fact table.

It contains one row per sales transaction and includes:

- transaction_id
- store_id
- product_id
- date_id
- sale_date
- quantity
- price
- discount
- revenue
- gst_amount
- payment_mode
- sales_channel
- customer_id
- cashier_id
- is_return

The model renames invoice_id to transaction_id and invoice_amount to revenue.
It also removes rows where the transaction ID is missing.

A fact table normally contains measurable business events. In this project, the
event is a sales transaction.


GOLD DIMENSION TABLES
---------------------
[Show the three dimension models]

1. dim_product.sql
   Stores distinct product attributes such as category, subcategory, brand,
   unit size, MRP, supplier, and shelf life.

2. dim_store.sql
   Stores distinct store attributes such as store name, city, district, state,
   store type, and area.

3. dim_calendar.sql
   Stores distinct date attributes such as date ID, calendar date, month, year,
   weekday, quarter, holiday, festival, and season.

A dimension describes the facts. Dimensions are used for filtering, grouping,
and putting labels on charts.

The dimensions connect to the fact table through keys:

    DIM_STORE[STORE_ID]       1 to many FACT_SALES[STORE_ID]
    DIM_PRODUCT[PRODUCT_ID]   1 to many FACT_SALES[PRODUCT_ID]
    DIM_CALENDAR[DATE_ID]     1 to many FACT_SALES[DATE_ID]

The dimension side is one because each key should appear once. The fact side is
many because many transactions can belong to one store, product, or date.


KPI MODEL
---------
[Open models/gold/kpi_sales.sql]

kpi_sales.sql aggregates fact_sales by store and sale date.

It calculates:

- total_revenue
- total_quantity_sold
- transaction_count
- average_basket_size
- return_transaction_count

This demonstrates that dbt can create business-level summary tables as well as
row-level fact and dimension tables.

For the Power BI dashboard, the same important KPIs are also created as DAX
measures so they respond immediately to slicers and chart selections.


MACROS
------
[Open the macros folder]

Macros are reusable pieces of Jinja and SQL. They help avoid repeating the same
SQL logic in many models.

This project contains three examples:

1. clean_text.sql

   The clean_text macro trims a column and turns an empty string into NULL.

2. safe_divide.sql

   The safe_divide macro divides one expression by another and uses NULLIF to
   prevent division-by-zero errors.

3. generate_schema_name.sql

   This macro controls the final schema name. It allows the project to create
   exact BRONZE, SILVER, and GOLD schemas instead of automatically combining
   schema names.

The first two macros are educational reusable examples. They are available for
future models; the current Silver SQL shows the logic inline so beginners can
see the transformation directly.

Why use macros?

- Reuse common logic.
- Reduce copy and paste.
- Make changes in one place.
- Generate dynamic SQL with Jinja.


SEEDS
-----
[Open the seeds folder]

Seeds are small CSV files stored inside the dbt project and loaded into the
warehouse as tables.

This project contains:

- payment_mode_lookup.csv: maps payment modes to Offline or Digital.
- store_type_lookup.csv: describes each store type.

Seeds are useful for small, stable reference data. They are not a replacement
for a large production ingestion system.

To load them:

    dbt seed

After loading, use ref with the seed name from another model, for example:

    {{ ref('payment_mode_lookup') }}


SNAPSHOTS
---------
[Open the snapshots folder]

Snapshots preserve historical versions of records when the source changes.
They answer questions such as:

- What was the product price before it changed?
- When did a store type or store attribute change?
- What values were active during a previous period?

This project contains:

- snapshot_products.sql
- snapshot_stores.sql

Both examples use a check strategy. dbt checks selected columns and creates a
new historical version when those values change. The unique key identifies the
record:

- product_id for products
- store_id for stores

To run snapshots:

    dbt snapshot

Snapshots are different from ordinary models. A model usually represents the
current transformed result. A snapshot keeps the history of changing records.


TESTS
-----
[Open the tests folder]

Tests protect data quality. A dbt test is a query where returned rows mean
failure. Zero returned rows means the rule passed.

This project contains two singular SQL tests:

1. fact_sales_no_negative_revenue.sql
   Finds transactions where revenue is negative.

2. fact_sales_valid_product_keys.sql
   Finds fact rows whose product ID does not exist in dim_product.

To run tests:

    dbt test

Tests are important because a successful SQL run does not always mean the data
is correct. The model can build successfully while still containing invalid
values or broken relationships.


RUNNING THE PROJECT
-------------------
[Show the terminal]

First, open PowerShell and activate the project environment:

    cd "D:\Study\DMart ETL"
    .\.venv\Scripts\Activate.ps1
    cd ".\DMartETL_DBT\dmart_ETL_project"

Check the connection and configuration:

    dbt debug

Build the entire project:

    dbt build

The build command runs enabled seeds, models, tests, and other selected dbt
resources according to their dependencies. It is the main command for a full
project workflow.

Useful focused commands are:

    dbt seed
    dbt run --select bronze
    dbt run --select silver
    dbt build --select gold
    dbt test
    dbt snapshot

For the Gold layer only:

    dbt build --select gold

The expected result is a summary with zero errors, for example:

    PASS=...
    WARN=0
    ERROR=0

Always run dbt from the folder containing dbt_project.yml.

POWER BI RELATIONSHIPS
----------------------
[Show Model view]

Create these relationships:

    DIM_STORE[STORE_ID]       1 to many FACT_SALES[STORE_ID]
    DIM_PRODUCT[PRODUCT_ID]   1 to many FACT_SALES[PRODUCT_ID]
    DIM_CALENDAR[DATE_ID]     1 to many FACT_SALES[DATE_ID]

Use Single cross-filter direction. Put each dimension on the one side and
FACT_SALES on the many side.

The relationships allow a selection such as Maharashtra or FMCG to filter the
fact table and update the entire report.


POWER BI MEASURES
-----------------
[Show the New measure button]

Create these measures in FACT_SALES:

    Total Revenue = SUM(FACT_SALES[REVENUE])

    Total Quantity = SUM(FACT_SALES[QUANTITY])

    Total Transactions = DISTINCTCOUNT(FACT_SALES[TRANSACTION_ID])

    Average Basket Size =
    DIVIDE([Total Revenue], [Total Transactions])

    Return Transactions =
    CALCULATE(
        [Total Transactions],
        FACT_SALES[IS_RETURN] = TRUE()
    )

    Return Rate = DIVIDE([Return Transactions], [Total Transactions])

Format revenue and average basket size as currency. Format Return Rate as a
percentage. Format counts as whole numbers.

Measures are better than manually calculated columns for dashboard KPIs because
they recalculate when the user changes a slicer.

TROUBLESHOOTING
---------------

If dbt says that dbt_project.yml cannot be found:

- Change directory to the folder containing dbt_project.yml.
- In this project, that folder is:

    D:\Study\DMart ETL\DMartETL_DBT\dmart_ETL_project

If dbt says the Snowflake adapter is missing:

    .\.venv\Scripts\python.exe -m pip install dbt-snowflake

If Power BI does not show new tables:

- Refresh the Snowflake Navigator or Power BI model.
- Confirm the selected database is DMART_ETL.
- Confirm the selected schema is GOLD.
- Run dbt build --select gold again.

If a relationship is many-to-many unexpectedly:

- Check that the dimension key is unique.
- Use DIM_STORE, DIM_PRODUCT, and DIM_CALENDAR on the one side.
- Use FACT_SALES on the many side.

For a free or low-cost setup, use Power BI Desktop locally and keep the
Snowflake warehouse small and suspended when it is not being used. Snowflake
warehouse compute can still cost credits.

Never show or commit passwords from profiles.yml in a video or repository.
Use environment variables or secure authentication in a real project.
